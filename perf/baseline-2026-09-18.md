# Línea de base de rendimiento — antes del Bloque 10

Fecha: 2026-09-18 · commit `ac5b649` · Next.js 15.5.23

Esto es el "antes" del guardarraíl que los tres tickets del Bloque 10
(VGRP-54, VGRP-55, VGRP-56) repiten: *se mide antes y después, con el mismo
método, y el número se anota*. Acá están los números y el método.

## Cómo reproducirlo (idéntico, después del bloque)

```bash
pnpm build                                  # guardar el bloque "Route (app)" del output
npx next start -p 3210
npx tsx scripts/perf-baseline.ts > perf/despues-<fecha>.json
```

`scripts/perf-baseline.ts` levanta Chromium contra el build de producción,
se loguea con los usuarios seed (`pnpm db:seed:test` si no existen) y navega
14 pantallas, 5 veces cada una. Reporta la mediana. No toca nada del sistema.

### Limitaciones del método, dichas de entrada

1. **El server corre en localhost, no en Vercel.** El salto browser→server es
   ~0 ms en vez de un viaje real al PoP. Los TTFB de abajo son entonces
   *pisos*, no lo que ve un usuario. Lo que sí es directamente comparable
   antes/después es todo lo demás: cantidad de viajes, cantidad de queries,
   peso del bundle, y el delta relativo de cada número.
2. **La base está prácticamente vacía** (ver más abajo). Los puntos 6 a 9 de
   VGRP-54 —el conteo que es un full scan, el índice faltante, el `select('*')`
   con `payload_raw`— **no son medibles hoy**: con 0 a 3 filas, un seq scan y
   un index scan tardan lo mismo. Ver "Lo que no se pudo medir".
3. `EXPLAIN` está deshabilitado en el proyecto (PostgREST devuelve 406), así
   que los planes hay que sacarlos del SQL editor de Supabase a mano.

### El hallazgo central de VGRP-54, confirmado empíricamente

En `/dashboard` y `/dashboard/principiante` con un usuario que pagó, los 4
fetches post-hidratación son exactamente los que nombra el ticket:

```
/api/agentes   /api/profesionales   /api/servicios-financieros   /api/perfil
```

**Objetivo del ticket: 0.** El costo hoy: la pantalla queda pintada a los
~120 ms y recién termina de tener contenido a los **~400 ms** — 280 ms
mirando tres "Cargando…". Ese delta (`hidratado − load`) es el número que
VGRP-54 tiene que llevar a ~0, y es el más honesto del informe porque no
depende de que el server esté en localhost.

Para el usuario que **no** pagó (`ninguno`), sobrevive 1 fetch: `/api/perfil`
desde `DashboardHeader`.

## 4. Clasificación de rutas en el build (VGRP-54 p.5, VGRP-55 p.3)

- `/dashboard` → **ƒ Dynamic**. Confirma el punto 5 de VGRP-54: es el único
  render dinámico del camino caliente, y está ahí sólo para leer un claim que
  el middleware ya leyó.
- `/dashboard/[variante]` → **● SSG**, con sólo `principiante` y `avanzado`
  prerenderizadas. Falta `ninguno`, que según el propio código es el estado
  más común. Confirma el objetivo del ticket.
- `/registro` → ƒ Dynamic (tiene su `force-dynamic`). Correcto.
- **`/comprar` → ƒ Dynamic.** Esto **no** coincide con lo que dice VGRP-55
  punto 3 ("Next la prerenderiza"). En este entorno sale dinámica, y la causa
  es identificable: `@vercel/edge-config` hace un `fetch` cuando `EDGE_CONFIG`
  está seteada (lo está en `.env.local`), y ese fetch opta la ruta a dinámica
  sola. **Hay que confirmarlo en un deploy real de Vercel antes de dar el bug
  por existente**: en Vercel el SDK puede resolver Edge Config desde un mount
  local sin fetch, y en ese caso el bug sí aparece. El arreglo (`force-dynamic`
  explícito) conviene igual —no depender de un efecto colateral del SDK—, pero
  el "antes" honesto de este punto es *sin confirmar*, no *roto*.

## Lo que no se pudo medir, y qué hace falta

1. **Los puntos 6–9 de VGRP-54 (trabajo de Postgres).** Con 0–3 filas no hay
   diferencia observable entre un full scan y un index scan. Para tener un
   "antes" real hace falta una de dos: correr los `EXPLAIN (ANALYZE, BUFFERS)`
   en el SQL editor de Supabase (el plan *shape* ya muestra el problema aunque
   sea rápido), o sembrar volumen realista antes de medir. Recomiendo lo
   primero para el conteo del ledger, que es el que el ticket pide explícito:

   ```sql
   explain (analyze, buffers) select count(*) from admin_pagos_ledger where sin_aplicar;
   select indexrelname, idx_scan from pg_stat_user_indexes where relname = 'pagos';
   ```

   (Lo segundo sirve también para confirmar que `pagos_proveedor_ref_idx` no
   tiene scans antes de dropearlo, como pide el punto 8.)

2. **Números de producción real.** Todo lo de arriba es localhost→Supabase.
   Los tiempos que ve un usuario salen de Vercel Speed Insights, que ya está
   instalado. Conviene anotar el percentil 75 de LCP/TTFB de la semana previa
   a arrancar el bloque como segundo "antes", porque es el único número que
   incluye el PoP, el CDN y la red del usuario.

3. **Las grillas con contenido.** `agentes` y `servicios_financieros` están
   vacías, así que el peso de las respuestas de `/api/*` y el trabajo de
   render de las grillas está subestimado. Si se carga contenido real antes de
   arrancar el bloque, conviene rehacer esta medición para no comparar contra
   un "antes" artificialmente liviano.
